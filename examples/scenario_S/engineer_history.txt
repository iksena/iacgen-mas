### Root Cause Analysis

- **Single finding, single root cause.** Iteration 1's `terraform validate` error is resolved (the `password` argument is gone). The only outstanding issue is a **Trivy AWS-0132 (HIGH)** finding: the artifacts bucket's default encryption uses `sse_algorithm = "AES256"` (SSE-S3 / AWS-managed keys), which the policy treats as "no customer managed key." The Rego rule fails when `bucket.encryption.kmskeyid` is empty — so the fix is to introduce a real CMK and point `kms_master_key_id` at it.
- **No Checkov errors and no structural errors are present**, so nothing to consolidate. The fix is additive: one new KMS resource plus an edit to the existing encryption configuration.
- **Downstream correctness consequence (not a validator error, but must be handled):** once objects are encrypted with SSE-KMS, the `test_role` launch-constraint role needs `kms:Decrypt` / `kms:GenerateDataKey` / `kms:DescribeKey` on that key, otherwise its `s3:GetObject` / `s3:PutObject` grants will fail at runtime. This is part of the same logical fix even though only the encryption line is flagged.

### Fix Objectives

1. **Create a customer managed key for the artifacts bucket** as a new `resource "aws_kms_key"` block (e.g. label `artifacts`). This is the object the encryption config will reference; do not introduce any hardcoded key ARNs or account IDs.

2. **Apply KMS hardening attributes on the key**: `description` referencing the artifacts bucket, `deletion_window_in_days` (e.g. 7 for a test stack), and `enable_key_rotation = true`. Add `tags = local.common_tags` so the key participates in the stack's tagging convention. This satisfies the CMK intent and is the expected best-practice companion to the AWS-0132 fix rather than a suppression.

3. **Optionally add an `aws_kms_alias`** (e.g. `alias/<project>-<environment>-artifacts`) pointing at the key ARN, so downstream Service Catalog/test tooling can reference a stable, human-readable name. This is optional but recommended; it must use `aws_kms_key.artifacts.arn`, never a literal.

4. **Update the existing `aws_s3_bucket_server_side_encryption_configuration.artifacts` rule** so `apply_server_side_encryption_by_default` sets `sse_algorithm = "aws:kms"` and `kms_master_key_id = aws_kms_key.artifacts.arn`. This is the direct fix for the AWS-0132 finding — it converts the "empty kmskeyid" state into a CMK-backed state.

5. **Add `bucket_key_enabled = true`** to that same SSE rule block. It keeps the CMK requirement satisfied while reducing KMS API call cost/volume for S3 traffic (S3 Bucket Keys), which is the recommended pairing for SSE-KMS on a data bucket.

6. **Extend the `data.aws_iam_policy_document.launch_constraint` policy document with a KMS statement** granting the launch-constraint role the operations it now needs against the CMK: `kms:Decrypt`, `kms:GenerateDataKey`, and `kms:DescribeKey`. Scope `resources` to `aws_kms_key.artifacts.arn` only (no `"*"` resource, no wildcard action pairing).
